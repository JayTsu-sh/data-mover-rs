## 修复和根因边界

**S3 源端：保留已验证的 HTTP 连接池修复。** SDK 默认运行时创建的 HTTP client 不一定出现在 `SdkConfig.http_client()` 中。仅克隆配置再造禁重试 GET client，可能产生第二个连接池。现有修复在实际发送请求时捕获并复用 SDK runtime 的 `SharedHttpClient`，同时保留 GET 禁自动重试与逐请求 QoS 计费。前一报告的真实 TCP 对照为旧版 baseline/high 2/3 次建连、修复后 2/2；本轮所有正常二进制都保留这项修复。不能把历史 S3→HDFS 的全部约 5% 差异唯一归因于连接池：此前 15 对主轮 97.969% 的失败仍在，独立 30 对确认为 99.928%。本轮重新实测 S3→HDFS，并列出相对和绝对对照。

**CIFS/NFS→S3：可复现的缓冲不足，吞吐收益仍须实测确认。** 原队列固定 4 块；CIFS/NFS 实际最大读块约 1 MiB，只有 4 MiB 队列，S3 MPU 分片却是 8 MiB。4 个分片上传占满窗口时，下一完整分片无法提前进入队列，源预读和目标上传之间出现额外背压。已撤回的实验候选由 staged destination 提供当前 stage 的写入单位提示，transfer engine 据源最大块大小调整队列。CIFS 此路径由 4 槽增至 8 槽，实际 NFS 最大块为 1 MiB−4 KiB 时增至 9 槽，分别多约 4/5 MiB 载荷；提示最多按 8 MiB 计算、最多 64 槽，原本缓冲足够的 Local/HDFS/S3 保留 4 槽，其他目标默认提示 0。S3 上传循环、4 路上传、8 MiB MPU 分片、源读并发和源请求粒度均保留。

该问题的真实 engine→S3 destination 回归测试先执行 RED：上传窗口占满后生产者停在 37 MiB，达不到下一完整分片需要的 40 MiB，2 秒超时。修复后 1/2/8 MiB 源块、无 QoS/高 QoS 六种组合均通过，同时检查完整 BLAKE3、6 个 MPU 分片、真实源计费字节和操作数。完整 debug fixture 的 GREEN 约 40 秒，测试内超时针对阻塞检测，不是整组测试耗时承诺。测试在归档的 `source-snapshot/crates/transfer/src/transfer/s3_input_buffer_tests.rs`，已随候选撤回；红绿日志也在归档。该测试证明了一个完整分片能否提前排队，不单独证明 98% 吞吐问题已经修复，也没有证明它是每一次历史磁盘低分的唯一原因。

**目标服务/磁盘是另一个测量变量。** 原目标 RustFS 使用 `/data/rustfs0`（设备 2049，和 NFS v4 目标同盘）；单独建立同一个 RustFS 可执行文件、独立端口和随机凭据的 `/dev/shm` 目标（设备 26）作为诊断对照。其作用是隔离磁盘变量，不能替代原磁盘验收。源端 CIFS 512 MiB 独立读对照 99.239%；高 QoS admission 累计仅约 0.35–0.38 ms。逐分片探针中，低分轮目标 RPC 累积耗时约 67.23 s，对照约 51.98 s；异步读跨度还包含未被轮询的背压，不能当成纯网络 RPC 延迟。SDK 实际 HTTP 探针中，每次 512 MiB 拷贝 64 个 UploadPart 各一次，未发现重传或 5xx。控制机 cgroup 没有 CPU throttling。以上是边界证据，不是对共享 RustFS 内部机制的唯一归因。

## 软硬配额、98% 利用率与请求压力

实验候选在原磁盘共复测 45 个有限配额场景：带宽 strict、带宽 soft/hard、IOPS strict、IOPS soft/hard、combined。IOPS 的现有口径是源 payload read，不包含元数据请求和目标写请求。使用旧已接受 `9b56c318` 的原始有限配额和命令参照；新增 S3→S3 使用单独记录的配置，历史结果为 null。生命周期由覆盖/即时删除改为唯一前缀/整组后清理，这项差异明确记录。本轮 512 MiB 与此前 512 MiB 使用同一 pattern；本轮 128 MiB 由该 pattern 重复生成，与此前报告 128 MiB 的随机内容不同。文件大小/配额/粒度/模式相同，但跨报告参照并非字节一致的原始数据复跑；同轮新旧二进制对照则使用完全相同输入。

- 原始判定 **338/345**，相对已接受参照的新增失败 **1**；完整失败项在 `checks.json` 和 `summary.json`。
- hard/soft 的判定作用于**源请求 admission**：任意区间满足 `hard×时间 + 一个有界实际请求`；soft 允许有限 burst，并验证 peak 后 steady ceiling/98% 利用率。离散请求不能要求任意无限短时间窗的瞬时速率都不超过数值限额。
- 端到端 98% 另计：包含准备、读写尾部、发布等；不能用 source admission 的通过替代端到端通过。严格 IOPS 的小文件/短预算容易受固定 RPC 尾部影响，所有相关失败保留。
- S3 带宽限制接受一个完整 GET 的量化误差，维持 8 MiB GET，128/512 MiB 分别为 16/64 个源 payload 请求；严格 IOPS 用例有独立受控请求大小。没有通过拆细带宽 GET 提高分数。S3→S3 为跨实例的 client-streamed 传输，确实计费完整源字节，不走未受限的 native copy。

对严格配额，设理想读源时间为 `N/Q`，正的上传/提交尾部为 `L`，端到端利用率至多约 `1/(1+L/(N/Q))`。16 次请求、1 IOPS 的 128 MiB 用例仅允许约 0.327 秒额外尾部才能达到 98%；此前实际 S3→S3 尾部约 0.550 秒，因此端到端失败与源调度正确可以同时成立。没有以提前免费发放一次 I/O 的方式更改原限速语义。

## 已否决的优化，避免带回回退

1. **仅将上传并发从 4 调至 8**：CIFS 绝对性能上升约 34%–41%，但目标 A/A 不可重复；Local 高/无仅 94.911%，HDFS 83.076%。未改默认值，也没有增加正式 preset。
2. **S3 consumer 内预取下一分片**：原型 SHA `31d779ec…` 在 CIFS 主组高/无为 104.255%，但 Local 新高/旧高为 96.268%；独立 12 个三臂块确认相对两组旧高分别只有 92.315%/93.030%。因此已撤回，原 S3 `staged/parts.rs` 与 9b 逐字节一致。原型源快照、红绿测试和全部真实失败仍归档，不能把原型通过当成当前版本通过。
3. **byte-aware producer 候选（已撤回）**：只改变小读块进入目标写入单位的队列容量，保留原 S3 writer。虽然减少了改动范围，原磁盘门槛及 Local 快速目标门槛仍有失败，不能按无回退接受。因此已撤回全部 8 个 Rust 文件变更；新测试及候选源代码完整保存在归档，保留版本不引入该接口或队列变更。拒绝候选不等于已经证明每个低分都由其代码引起；它表示证据不足以满足用户的无回退验收。

## NFS 追加根因对照（不覆盖主轮失败）

在相同候选、原磁盘目标上追加预先固定的 6 个三臂块，共 18 次 512 MiB：A/A 的 95% 区间 `[0.8155512125235828, 1.0965762385330746]`，高/无 QoS 为 100.281%，`qualified=False`。使用同一 idle/完整哈希/新目标前缀/整组后清理，没有替换上表 NFS 主轮判定。

独立 NFS4.1 读源使用专用、明确开启完整读窗口的 source-only 探针（NFS/QoS 代码与 9b/实验候选相同），4 对原 512 MiB，baseline/high 分别 1958.246/1801.718 MiB/s，比值 92.007%。它不包含目标上传，属于诊断，不能当作端到端通过。该 512 MiB 诊断**失败**，不能隐藏：单次 baseline 0.228–0.282 s、high 0.265–0.288 s，都是 515 次请求、每次最大 1,044,480 字节，未发生请求膨胀。追加的高/无比值区间为 `[0.79465,0.98128]`，未具备 2% 认证精度，也不能仅凭它把 NFS 源侧排除。

因此在初次清理后，仅重新创建本 run 的 NFS 源数据，使用同一个 1 MiB pattern 增加**独立 4 GiB 纯读诊断**，6 个预先固定的 A/A/high 平衡块。该试验不替换原 512 MiB 和端到端失败。4 GiB 高/无为 103.190%，A/A 95% 区间 `[0.8614708366632962, 1.1669514283836935]`，高/无 95% 区间 `[0.9319671072857011, 1.1788609018699565]`，`qualified=False`。同时记录每个子进程 CPU 与上下文切换；采样后在 finally 中删除重新创建的 NFS 源目录和本地 4 GiB fixture，清理结果追加到原记录，初次记录独立保留。4 GiB 的子进程 user CPU 中位数 baseline/high 约 2.452/2.448 s、system CPU 约 3.000/2.729 s，包含本地预读 hash 和连接准备，不能当作仅计时区间的 CPU。未观察到稳定的每字节 CPU 增量，但 A/A 仍不可重复，不能认证 2% 差异，也不能以长测覆盖 512 MiB 失败。追加组首次还在未使用的 Local 根目录连接阶段被拦截，0 个计时源读取样本；创建该空目录后按原计划重试，原错误和首次清理结果均保留。
