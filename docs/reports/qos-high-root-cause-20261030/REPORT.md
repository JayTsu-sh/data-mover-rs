# 两项高 QoS 失败：根因、修复与回归验证

日期：2026-10-30（Asia/Shanghai）。隔离 run：`nightly-qos-high-20261029234234`。

**确认并修复了 S3 高 QoS 读取丢失已建立 HTTP 连接池的问题。** 在相同 512 MiB、随机均衡的 12 个区组中，原版高 QoS / 原版基准为 95.878%，修复版为 **99.973%**；新版高 QoS / 原版高 QoS 为 **106.703%**，新版无 QoS / 原版无 QoS 为 **102.333%**。真实 TCP 连接数从高 QoS 的 3 个降至 2 个，与无 QoS 一致。

NFSv4.1→S3 的原失败没有复现为稳定的限速器退化：原版新隔离对照为 100.608%，分阶段探针显示源读约 0.36 秒，而写入背压约 11.9 秒；目标 VM 同时存在明确 I/O 等待。最终原尺寸 15 组复验为 **98.917%**。其主要问题是目标存储波动下的短样本归因，不能虚称修复了一个已证实的 NFS 调度缺陷。

S3→HDFS 的主矩阵 15 组结果仍为 **97.969%，未通过**；随后独立预定的 30 组原尺寸复验为 **99.928%，通过**。后者不覆盖前者。CIFS→S3 的额外对照仍观察到相对同版基准 **91.637%，未通过**，但新版高 QoS 相对原版高 QoS 为 **101.700%**，未观察到本次修复引入的绝对性能下降。

最终 23 路高 QoS 判定通过 **20/23**；主回归 **944/955** 项通过。八条涉及 S3 的路径另按上轮完全相同有限配额执行 40 次复制、304 项判定，新增失败 **0** 项。历史 strict 短文件不达标与本次新增失败分别列出，不声称覆盖全部文件、缓存及外部负载的绝对无回退保证。

## 1. 两项问题分别是什么

### S3→HDFS：克隆配置没有携带 SDK 的默认 HTTP client

原实现为保证每次 GET 重试重新扣带宽/IOPS，预构建一个关闭 SDK 自动重试的 client：`Client::from_conf(client.config().to_builder().retry_config(disabled).build())`。但 SDK 的默认 HTTP client 由 runtime plugin 注入，**并不保存在原 `Client::config()` 中**。因此克隆配置创建了另一套连接池。元数据/无 QoS GET 已建立的连接，QoS GET 无法复用；准入 trace 中的零等待无法看见这项传输层开销。

证据来自两种独立执行路径：

- 本地真实 TCP 回归测试执行 HEAD、普通 GET、HEAD、带 QoS GET；不依赖 mock 的连接数估计。移除 transport 复用后 **2 个连接、期望 1 个**，测试在约 0.06 秒内失败；恢复修复通过。HTTP 数据仍走真实 SDK 和公开 `ReadSource`。
- lab 的真实 512 MiB S3→HDFS 复制，`strace -f -e connect` 计数：原版无 QoS **2**、原版高 QoS **3**；修复版两者均 **2**。包含元数据与 payload 的 TCP connect，**不等同于 GET 次数**。带 strace 的耗时不参与性能通过判定。

修复只捕获并复用 SDK 运行时实际选中的 `SharedHttpClient`，在连接/元数据阶段完成；单次尝试 client 仍预构建，原来的默认 transport、TLS/代理选择、请求尺寸和并发均保留。显式自定义 transport 直接复用。逐次重试扣费、取消、对象版本/ETag 绑定不变，未增加免费首包或跳过 QoS。最终没有新增依赖、升级版本或修改 Cargo.lock。

实现见 [qos_client.rs](../../../crates/backend-s3/src/backend/client/qos_client.rs)、[连接初始化](../../../crates/backend-s3/src/backend/client.rs)、[GET 调用](../../../crates/backend-s3/src/backend/client/role_protocol.rs)、[真实 TCP 回归测试](../../../crates/backend-s3/src/backend/client/role_protocol/qos_pool_tests.rs)。

另外用保留最大源并发的独立 source-only 诊断二进制，去掉 HDFS 写入和关闭，完成同样 512 MiB 的 12 区组、48 次完整哈希读取：原版高 QoS / 原版基准 **100.400%**，修复版 **100.497%**，每次仍为 64 个 8 MiB payload。**原版也没有稳定的源读取吞吐退化，所以不能把旧的 5.18% 差额全部归因连接池。** 原版分阶段五组中 HDFS close 中位数为无 QoS 148.47 ms、高 QoS 162.81 ms；完整复制还包含冷启动、目标消费、关闭和发布的波动。source-only 只用于归因，未代替复制验收。

原失败 94.822% 的全部差额没有历史分阶段服务端日志，不能把每一毫秒都归因连接池；本次已确定独立可复现的代码缺陷，并在旧版再次失败的同一对照实验中验证修复，而非用延长文件或放宽 98% 阈值通过。

### NFSv4.1→S3：目标 I/O 瓶颈和抽样波动，源调度不是主导开销

同一原版二进制 `d7c04f…` 在新隔离环境，512 MiB、10 组交替对照为 **100.608%**；上轮无 QoS A/A 就有 107.412% 的组间比值。不能把一次 96.123% 点估计当成稳定、可重复的 QoS 代码退化。

原版分阶段诊断五组的中位数如下；这些是诊断数据，未混入正式通过样本：

| 阶段 | 无 QoS | 高 QoS |
|---|---:|---:|
| producer 总时长 | 12.409 s | 12.658 s |
| 源 stream 等待累计 | 0.360 s | 0.360 s |
| 向目标队列发送等待累计 | 11.864 s | 12.165 s |
| 源哈希累计 | 0.144 s | 0.143 s |
| S3 EOF 后分片排空 | 0.080 s | 0.067 s |
| CompleteMultipartUpload | 0.184 s | 0.136 s |

队列等待主要来自目标写入背压；源读取和 QoS 准入都不是这些约 13～17 秒复制的主导耗时。上轮准入专项仅累计约 0.266 ms、0 次限速等待。目标 VM 的本次只读采样进一步显示 8 vCPU、内存充足，但 I/O PSI 的 `some avg10=40.01%`、`full avg10=39.12%`，复制活跃段 CPU iowait 约 13～21%，写入约 25～49 MiB/s，吻合实际吞吐与波动。

这证明当前路径受目标 I/O 约束，与原样本波动一致；**没有旧失败时刻的同等服务端遥测，不能宣称已定位那个时刻的具体磁盘请求。** 本次保留 NFS 调度实现，使用原尺寸复测、完整旧版对照及目标遥测修正归因；没有停止服务、修改存储参数或用更大文件覆盖旧失败。

## 4. 保持上轮配额不变的额外回归
