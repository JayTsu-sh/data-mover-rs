# 架构 review

代码 review 必须检查职责归属、模块边界和逻辑内聚性。相关逻辑应集中在合理的所属模块，避免跨层泄漏、重复实现、分散特判和无实际价值的转发层。发现本次改动引入或加重的结构问题，应提出合理的组织方案并在合入前解决；测试通过不能替代架构审查。

## 检查与结论

- **职责归属**：业务策略、通用机制、协议细节和状态各由谁负责；调用方是否承担了应封装在模块内部的复杂度。
- **规则集中**：错误分类、恢复预算、计数和状态转换是否存在重复实现或多个判断入口，使同一改动需要四处同步。
- **有效拆分**：文件、函数和模块是否形成清晰职责，避免一个流程被拆为大量相互依赖的小片段，也避免无关职责堆入同一模块。
- **合理方案**：依据职责、依赖关系与可维护性决定组织方式，不以改动范围小、文件少或新增抽象作为合理性的依据。

发现问题时给出具体位置、影响、应归属的模块及调整理由，区分本次必须修复的问题与无关历史问题。结论须覆盖最终提交，不能只写“建议重构”或“注意解耦”。

## 本仓库的审查重点

保持 facade、model／ACL、storage-core role、通用引擎和 backend 的依赖方向；backend 能力与行为一致。检查调度策略、错误分类、恢复、计数是否重复，是否把具体协议或产品任务决策泄漏到通用流程。
