## Findings that determine the design

The requested facility is **proposed**, not implemented: preserve source-derived standard BLAKE3 state and a completed-range bitmap at the destination; resume without rereading source bytes for reusable ranges; compare destination bytes with the computed/restored source digest; remove checkpoint artifacts when released. No permanent success manifest is required.

Current recovery is prefix-based. `PreparedStage.write_offset`, `CheckpointObservation.durable_prefix`, and the pointer codec have no persisted range bitmap or source hash state ([stage:10](../../src/storage/roles/stage.rs#L10), [roles:230](../../src/storage/roles.rs#L230), [pointer:36](../../src/storage/pointer.rs#L36)). `WriteProgress::Confirmed` explicitly does not establish durability or recovery authority; `Checkpoint` reports only a prefix ([write_progress:5](../../src/storage/write_progress.rs#L5)). Neither callback is an adequate persistence hook for the new facility.

At this SHA, the ordinary transfer producer calls ordered `ReadSource::read`, hashes in file order, and sends a four-item byte queue. On a resumed transfer with verification enabled it sets `read_start = 0`, hashes the prefix again, and suppresses those bytes from writes; the expert source path also always requests a full source hash ([payload:34](../../src/transfer/engine/payload.rs#L34), [producer:15](../../src/transfer/engine/producer.rs#L15), [producer:96](../../src/transfer/engine/producer.rs#L96), [expert:139](../../src/transfer/engine/expert.rs#L139)). Local/NFS/CIFS positioned writers and Local/NFS/CIFS/HDFS positioned readers exist, but inspection found no `read_positioned`/`write_positioned` caller in `src/transfer` or `src/runtime`. The architecture's statement that ordinary mixed-backend transfers already use that path is ahead of these engine call sites ([architecture:531](../architecture/storage-transfer-architecture.md#L531)). Treat the adapters' positioned methods as implemented capabilities, not proof of an active ordinary unordered engine.

Do not infer write size from source size: a Local 2 MiB read can become many small negotiated NFS writes; an S3 8 MiB source chunk can become one Local task; small NFS reads accumulate into an S3 part. A resumed native S3 upload can retain 64 MiB parts even after switching to streaming. This is why persistent hash/bitmap addressing must use **absolute logical byte offsets**, independent of transport chunks and today's concurrency.

Main-agent live evidence supplied during this research (not independently probed or artifact-reviewed here): read-only mounts with production `nfs-rs 0.8.6` against `10.128.56.160` / `.161`, export `/nfsrs_pnfs_b`, reported read/write **1,044,480 bytes (1020 KiB)** and `pnfs=true`. On the user-provided AFX test host `10.128.56.17`, the completed userspace `nfs-rs 0.8.6` probe against `192.168.9.101:/pnfs_test2` negotiated read/write **65,536 bytes (64 KiB)**, matching the previously reported kernel-mount sizes. These are observed limits for those connections, not universal defaults.

The main agent reports three **16 MiB + 123 byte** AFX trials with actual nondegenerate DS traffic to `.103` / `.102` / `.104` on `192.168.9.0/24`: packet conversations showed approximately **33 MB read + 17 MB write on DS connections versus 11 KB on the MDS**. Reads mixed **32,771 / 49,157 / 65,536 byte** requests with eight requests in flight, with every byte verified. Unordered delivery had **169 / 181 / 170 of 342** completions outside their issue-order positions in the respective trials; ordered delivery had **0**. Files were removed, unmount succeeded, and the packet capture reported zero drops. An initial degenerate MDS-only trial had **38/342** unordered completions outside issue-order positions; retain it as separate evidence, not as a multi-DS result. The three later trials establish DS participation and observable logical-read completion reordering; these aggregate packet counts do not prove concurrent activity across multiple DS servers or individual stripe delivery before aggregate READ completion.

Separately, existing machine-local `probe-fast` / control logs for **20 GiB** report parallel depth four at approximately **20.4 / 21.86 seconds**, versus sequential at approximately **43 seconds**. These are historical log observations supplied by main, not fresh measurements from the trials above, and do not establish multi-DS concurrency. No new throughput claim is inferred from them.

There are **two head-of-line blocking layers** to distinguish. Main reports that the newer dirty dependency's `pnfs_read_layout` (lines 874–899) uses `try_join_all` and concatenates DS stripe buffers: a slow stripe delays completion of its entire logical READ. That report is not evidence that the pinned registry implementation is identical. Independently, this adapter exposes one `cursor.read_at(offset, count)` future per logical range; ordered mode uses `FuturesOrdered`, while positioned mode uses `FuturesUnordered` ([source:251](../../src/storage/backends/nfs/source.rs#L251), [read submission:353](../../src/storage/backends/nfs/source.rs#L353)). The ordinary producer adds ordered source delivery/hash consumption. Unordered range hashing/positioned delivery can remove the wait for earlier **logical READs**, but cannot emit an individual DS stripe before the dependency finishes the aggregate READ. No stripe-streaming dependency API or NFS dependency change is proposed here; any latency claim must identify which layer it removes.

## Persistence, short operations, and evidence

### Local

`write_all_at` loops on short writes, retries interrupted syscalls, and rejects zero or excessive counts ([staged:62](../../src/storage/backends/local/staged.rs#L62)). The positioned writer tracks received and completed interval frontiers, detects overlaps, and requires hole-free final coverage ([positioned:18](../../src/storage/backends/local/staged/positioned.rs#L18)). It drains issued writes before checkpointing, but persists only the contiguous frontier ([positioned:205](../../src/storage/backends/local/staged/positioned.rs#L205)). A successful positional write or a large sparse file length is insufficient evidence.

Checkpoint publication already has the appropriate ordering: data sync → pointer bytes to a newly created fixed temporary → temporary `sync_all` → rename → directory sync ([data sync:680](../../src/storage/backends/local/staged.rs#L680), [checkpoint:36](../../src/storage/backends/local/staged/checkpoint.rs#L36)). A new range record could use this replacement boundary, but current resume truncation would destroy otherwise retained suffix ranges and must change ([prepare:316](../../src/storage/backends/local/staged/at_destination.rs#L316)). The claim protects cooperating same-kernel processes, not arbitrary writers on a remote mount ([Local notes:107](../../.claude/docs/storage-local.md#L107)).

### NFSv3 / v4.0 / v4.1

Primary semantics: [RFC 1813 §3.3.7 WRITE](https://www.rfc-editor.org/rfc/rfc1813.html#section-3.3.7) returns the accepted count, committed level, and verifier; a successful short write requires sending the remaining suffix. §3.3.21 COMMIT flushes unstable bytes; its verifier must agree with the write evidence, or the client must retransmit affected data. [FSINFO §3.3.19](https://www.rfc-editor.org/rfc/rfc1813.html#section-3.3.19) supplies separate `rtmax`/`wtmax`. The adapter's 1 MiB cap is its policy, not an NFS protocol maximum.

For v4.1, [RFC 8881 §18.32 WRITE](https://www.rfc-editor.org/rfc/rfc8881.html#section-18.32) and [§18.3 COMMIT](https://www.rfc-editor.org/rfc/rfc8881.html#section-18.3) preserve count/stability/verifier requirements. [§5.8.2.20–21](https://www.rfc-editor.org/rfc/rfc8881.html#section-5.8.2.20) defines server `maxread`/`maxwrite`; session request-size and slot negotiation also constrain execution. v4.0's corresponding operations are [RFC 7530 §16.32](https://www.rfc-editor.org/rfc/rfc7530.html#section-16.32) and [§16.3](https://www.rfc-editor.org/rfc/rfc7530.html#section-16.3). Session replay safety does not replace stable-storage evidence.

Current adapter implementation:

- `role_write_unstable` loops over accepted counts, retains partial accepted work on failure, and rejects invalid counts ([client:1187](../../src/storage/backends/nfs/client.rs#L1187)). Non-FILE_SYNC outcomes retain source payload in memory for replay ([client:640](../../src/storage/backends/nfs/client.rs#L640)). This is intra-process replay state, not a persisted source hash.
- `checkpoint_deferred_writes` serializes against writes, passes the complete outcome batch to `commit_write_batch`, and retries verifier-change failures by replaying retained payload, up to three commit attempts ([client:683](../../src/storage/backends/nfs/client.rs#L683)). Correctness of the dependency's wire behavior is not independently audited here.
- The writer drains before its checkpoint barrier, then records the pointer; it uses separate issued/completed frontiers, checks short counts, and rejects holes on successful finish ([positioned:198](../../src/storage/backends/nfs/positioned_writer.rs#L198), [count handling:243](../../src/storage/backends/nfs/positioned_writer.rs#L243), [finish:329](../../src/storage/backends/nfs/positioned_writer.rs#L329)). On error the finishing path can truncate the stage to a retained prefix ([staged:270](../../src/storage/backends/nfs/staged.rs#L270)). Both resume truncation and error truncation need auditing for range preservation.
- Pointer extension is `DMNSTG01` plus a prepare nonce. Rewrites, rename publication, and cleanup check ownership. This is a fence check, not a distributed lock; one-writer-per-key remains a caller contract ([at_destination:1](../../src/storage/backends/nfs/at_destination.rs#L1), [pointer write:387](../../src/storage/backends/nfs/at_destination.rs#L387)). A new hash/bitmap generation must share that fence. A stale verifier must never promote ranges to durable merely because WRITE returned success.

### CIFS/SMB

[MS-SMB2 §2.2.17 FLUSH](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/e494678b-b1fc-44a0-b86e-8195acf74ad7) requests persistence of cached information for the identified open. Negotiated [MaxReadSize/MaxWriteSize](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/00a5a917-e5f9-4d31-a0d5-a5ee7209c61f) are connection/server limits, not a universal 1 MiB size; effective facade capability can be smaller. The actual connected values and credit behavior are unmeasured here. FLUSH does not establish POSIX parent-directory fsync semantics.

The sequential writer drains, FLUSHes, then writes its pointer; the positioned writer verifies gap-free received/completed frontiers before final FLUSH ([writer:98](../../src/storage/backends/cifs/writer.rs#L98), [save:120](../../src/storage/backends/cifs/writer.rs#L120), [positioned:279](../../src/storage/backends/cifs/positioned_writer.rs#L279)). Pointer data is itself written exactly and FLUSHed before rename ([at_destination:403](../../src/storage/backends/cifs/at_destination.rs#L403)). The facade's `write_all_at` owns short-write completion; this repository does not inspect its internals. Persist range coverage after FLUSH, preserving the existing nonce fencing. File length cannot identify holes; the absence of truncation is not evidence that an old suffix is reusable.

### HDFS

Apache's [output-stream contract](https://hadoop.apache.org/docs/r3.3.6/hadoop-project-dist/hadoop-common/filesystem/outputstream.html#Durability) distinguishes `hflush` visibility from `hsync` persistence. Its Java HDFS caveats concerning `dfs.datanode.synconclose` and current-block-only `hsync` are background, **not the actual pinned Rust close policy**. [HdfsDataOutputStream](https://hadoop.apache.org/docs/stable3/api/org/apache/hadoop/hdfs/client/HdfsDataOutputStream.html) also distinguishes sync flags affecting NameNode length. The pinned Rust source below determines this adapter's behavior.

Current adapter invokes `hsync` at intermediate checkpoints and then checks stat size; final write and temporary pointer write use `close` ([writer:38](../../src/storage/backends/hdfs/writer.rs#L38), [checkpoint:102](../../src/storage/backends/hdfs/writer.rs#L102), [pointer temporary:439](../../src/storage/backends/hdfs/at_destination.rs#L439)). The adapter delegates both operations to the fixed `hdfs-native` writer ([role_protocol:340](../../src/storage/backends/hdfs/client/role_protocol.rs#L340)). Absence of another facade-level `hsync` does not imply absence of DataNode synchronization.

Main's additional dependency inspection is confirmed against official source at fixed revision `695fc47e9f88804e39bba1d30bf128e66da9b8d6`:

- [`WritePacket::set_last_packet`, connection.rs:604](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/hdfs/connection.rs#L604) always sets the sync-block flag.
- [`ReplicatedBlockWriter::close`, block_writer.rs:750](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/hdfs/block_writer.rs#L750) sends the remaining data, sends that final sync-marked packet, and awaits pipeline shutdown, including acknowledgement/recovery handling. [`hsync`, block_writer.rs:685](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/hdfs/block_writer.rs#L685) sends a sync-marked packet and waits for its acknowledgement.
- [`FileWriter` block rollover, file.rs:340](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/file.rs#L340) closes the previous block before allocating the next. [`FileWriter::hsync`, file.rs:403](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/file.rs#L403) synchronizes the current block then calls NameNode `fsync`; [`FileWriter::close`, file.rs:420](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/file.rs#L420) closes its block then completes the file.

Thus the replicated Rust path requests acknowledged DataNode sync at block close, including rollover and final/pointer-file close; the earlier blanket uncertainty about whether it syncs previous blocks is resolved at the source-policy level. Erasure-coded `hsync` remains explicitly unsupported ([block_writer.rs:90](https://github.com/kimahriman/hdfs-native/blob/695fc47e9f88804e39bba1d30bf128e66da9b8d6/rust/src/hdfs/block_writer.rs#L90), returning `OperationFailed` with that diagnostic). These code facts do not certify real server/device power-loss behavior or the proposed checkpoint's crash consistency.

Recovery closes the lease and trusts the recovered stage length, opting into `continues_from_stage = true`, instead of stopping at the pointer's last hsync'd prefix ([at_destination:231](../../src/storage/backends/hdfs/at_destination.rs#L231), [opt-in:272](../../src/storage/backends/hdfs/at_destination.rs#L272)). Consequently a hash record saved only with the old pointer can lag reusable destination bytes. HDFS cannot fill arbitrary holes with the existing append-only writer. Keep unordered hashing/source reads separate from destination ordering: bound the reorder buffer and persist a hash-covered append prefix. To keep recovered tails without source rereads, durable source-hash intent must cover every potentially retained append, or recovery needs another justified reconstruction mechanism; silently rereading/truncating that tail fails the requested behavior.

### S3 object buckets and compatibility profiles

[AWS multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html), consulted 2026-10-22: 10,000 parts, numbers 1–10,000, 5 MiB–5 GiB per part except the final part has no minimum, 1,000 results per `ListParts` page, and a currently documented maximum object size of 48.8 TiB. Do not substitute an older 5 TiB assumption. The adapter's 8 MiB read/part defaults and 64 MiB native sizing are library policies.

[AWS multipart lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html) permits unordered part upload and replacement of a part by reusing its number; completion uses part numbers and ETags in object order. [AWS checksums](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html) distinguish full-object and composite checksums; ETag is not generally whole-object MD5, and these APIs do not provide the requested standard BLAKE3 state. Additional-checksum workflows require consecutive part numbers from 1 at completion. AWS behavior must not be assumed for all compatible services.

The implemented pointer contains no durable prefix: `DMS3UP01`, nonce, part size, and upload id; ListParts is the evidence ([upload_pointer:1](../../src/storage/backends/s3/staged/upload_pointer.rs#L1)). Discovery sorts parts but stops at the first gap/size mismatch, so later valid parts are deliberately retransmitted ([upload_discovery:27](../../src/storage/backends/s3/staged/upload_discovery.rs#L27)). A proposed unordered recovery path must retain all validated parts, intersect their exact ranges with persisted source hash coverage, and schedule only missing parts. Final completion must still contain the entire logical object with valid part sizes and order. It cannot simply complete a gapped list and claim that original offsets were preserved.

`upload_parts` slices incoming Bytes into an aggregate `S3Body`, limits concurrent uploads, sends Content-MD5, and records returned ETags ([parts:63](../../src/storage/backends/s3/staged/parts.rs#L63), [part request:19](../../src/storage/backends/s3/client/role_protocol/multipart.rs#L19)). Hash state must survive this aggregation and distinguish original source evidence from transport MD5. Current part facts passed toward completion are numbers/ETags, not BLAKE3 proofs. Persist upload id, frozen part geometry, size, part number/ETag and generation binding with the new recovery data; detect replacement rather than accepting stale bitmap bits. The stream writer's memory window adjusts downward when resuming larger native-copy parts ([final_upload:142](../../src/storage/backends/s3/staged/final_upload.rs#L142)).

`compat` changes request behavior and native affinity; `bucket_type` chooses capabilities ([architecture:59](../../src/storage/backends/s3/client/architecture.rs#L59)). Standard, DXN and ONTAP object profiles permit native pairs only within matching affinity; StorageGRID disables native. DXN tags are unsupported. NAS additionally restricts native copying to the same bucket ([architecture:34](../../src/storage/backends/s3/client/architecture.rs#L34)). Thus `compat=ontap` alone does not imply nonresumability; `bucket_type=nas` does.

For NAS, persisted HEAD ETags are modeled as mtime/size-derived and conditional reads are unavailable; checks bracket the read rather than pinning immutable content. The library's 5 GiB write cap is a design policy, not the measured server maximum ([capabilities:31](../../src/storage/backends/s3/capabilities.rs#L31), [limits:1](../../src/storage/backends/s3/staged/limits.rs#L1)). It cannot satisfy a stronger no-reread resume promise without a new supported staging mechanism. The current atomic last-byte-held single PUT remains an explicit unsupported-recovery case.

## Verification, native bypass, and final cleanup

Current transfer verification already passes the source's computed digest into `VerifyRequest.expected_blake3`; it does not replace it with a destination-computed expectation ([publication:101](../../src/transfer/engine/publication.rs#L101)). However, standalone `integrity::compare(Content)` hashes both complete objects and has no supplied-source-digest input ([integrity:254](../../src/integrity/mod.rs#L254)). A final compare for this feature must consume the recovered/computed source digest and read the destination only, rather than invoke that existing two-sided content comparison unchanged.

Native S3 copy bypasses source payload streaming. When read-back is enabled, the current engine hashes the **entire source before preparing/copying**; when disabled, it has no source digest ([native:67](../../src/transfer/engine/native.rs#L67)). Existing native multipart recovery can share an upload with streamed recovery, but service-side copy receipts do not produce BLAKE3 source state. For the new guarantee either stream the source through the resumable hash path, or implement a separately checkpointed source-hash pass with explicit native integration. Do not silently select native and claim all source bytes were hashed only once across restarts.

Current successful `publish` is documented to leave no stage or pointer, and discard deletes the pointer before stage content ([roles:494](../../src/storage/roles.rs#L494)); there is **no existing standalone `release_checkpoint` method** on this trait. The requested checkpoint-release operation is a proposed lifecycle seam: **release removes the checkpoint pointer and its owned hash/bitmap generations; it does not create or retain a permanent success manifest**. Preserve destination ownership/fencing and idempotence, and distinguish release of recovery metadata from deletion of final content.

If hash/bitmap state must support a crash during final comparison, it must remain recoverable through that comparison. S3 currently deletes its pointer inside publish, before read-back; integration must explicitly revise that ordering/contract or retain temporary post-publication verification state bound to the exact committed object/version. MPU parts cease to be evidence after completion. A temporary committed phase is compatible with eventual checkpoint release and does not imply permanent success state. Without such a change, interruption after S3 publication can require a fresh source hash on the next attempt. Post-commit mismatches cannot be reported as an unchanged destination ([engine:222](../../src/transfer/engine.rs#L222), [verify_published:12](../../src/transfer/engine/publication.rs#L12)).

## Proposed integration requirements for the main design

1. **Separate three geometries.** Keep hash tree addressing, bitmap coverage units, and backend read/write/part boundaries distinct. Store absolute offsets/lengths, source size/version binding, and any frozen upload geometry. Rechunking or changing negotiated rsize/wsize must not reinterpret a prior bitmap. Track partial-unit coverage until complete; never round a short write or hole upward.
2. **Preserve standard BLAKE3.** Ordinary per-buffer BLAKE3 digests cannot simply be hashed together to obtain whole-file BLAKE3. The official [BLAKE3 hazmat implementation](https://github.com/BLAKE3-team/BLAKE3/blob/master/src/hazmat.rs) distinguishes non-root chaining values, positional subtree constraints, and root finalization, including the special single-chunk case. The main hash design must specify a portable versioned representation, correct tree offsets, partial boundary state, and final-root material; a raw memory dump of `Hasher` is not a recovery format. Small negotiated chunks and byte-sized checkpoint boundaries must not force rereading already covered source fragments.
3. **Checkpoint a consistent generation.** Completed durable ranges and source-derived hash evidence must agree. Data barrier → durable hash/range generation → atomic pointer reference is the normal publication order; after a crash adopt only a complete generation that passes binding, checksum, and backend recovery checks. One generation must not reference another's bitmap or hash frontier. Existing `DMDPTR01` extension is limited to **4 KiB**, so a scalable bitmap/frontier requires a new format or destination-resident generation objects rather than unbounded extension growth ([pointer:23](../../src/storage/pointer.rs#L23)).
4. **Close the data-ahead-of-hash window.** HDFS recovered tails and S3 listed parts can be discoverable after a crash even when the latest hash-state commit was lost. To retain those bytes without source rereads, persist sufficient source-hash intent **before** allowing those bytes to become independently recoverable, then reconcile it with authoritative destination evidence. Intent alone must not mark bytes complete. A scheme that merely drops all such ranges or restarts HDFS cannot claim the requested reuse guarantee. Clarify behavior for legacy checkpoints that contain no source hash: the guarantee cannot be retroactively manufactured from a prefix number or ETag.
5. **Let each destination prove its own ranges.** Local/NFS/CIFS need durable range records and must stop truncating/forgetting saved suffixes; HDFS retains an append prefix and bounded reordering; S3 retains independently validated parts and a missing-part schedule. Existing positioned-write contracts require contiguous coverage from a single recovery offset on successful return, so sparse-resume scheduling needs an explicit contract extension ([roles:308](../../src/storage/roles.rs#L308)). No uniform bitmap justifies pretending all destinations accept positioned writes.
6. **Keep source evidence authoritative.** Final expected digest comes from restored source hash state plus newly read missing source ranges. Destination bytes may be read for final verification; their freshly computed digest cannot stand in as the expected source digest. Validate the same source content binding across attempts, retaining existing immutable S3 version pins and documenting weaker filesystem/NAS mutation observations ([binding:159](../../src/transfer/engine/plan.rs#L159), [S3 version pin:46](../../src/storage/backends/s3/source.rs#L46)).
7. **Bound memory and temporary storage.** A stalled low offset must not retain arbitrarily many completed payloads; unordered hashing should compact hash nodes while respecting backend order and read admission. Also bound active hash generations, retained S3 versions, part bodies, and HDFS pending hash intents. Current source queue capacity alone does not bound a future hash frontier or part aggregator.
8. **Finish, compare, release.** Require full logical byte coverage and correct EOF before root finalization; verify at the backend's supported point using that root; preserve truthful committed-state failures; release pointer plus owned checkpoint generations once the checkpoint lifecycle ends. No permanent success manifest, source reread pass, or universal native bypass is implied. NAS/single-PUT paths must report their actual unsupported recovery rather than advertise partial reuse.
