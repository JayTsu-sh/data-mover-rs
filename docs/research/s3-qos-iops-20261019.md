# S3 source IOPS semantics and low-bandwidth request amplification

Date: 2026-10-19. Baseline investigation and subsequent implementation follow-up.

## Implementation follow-up

The findings below describe baseline `6f083e2`, before the requested fix. The
subsequent implementation changes both source behavior and lab expectations:

- S3 uses whole-request admission, preserving its configured read/request cap
  independently of the 10 ms bandwidth quantum. The source waits for the entire
  bounded GET's byte cost before dispatch. Other source backends retain their
  existing fine-grained admission behavior.
- QoS GETs disable SDK retries and use at most three source-owned attempts per
  range. Every retry re-enters the shared IOPS and bandwidth scheduler with the
  same source identity conditions and range. Failed attempts reserve bandwidth;
  returned payload statistics count complete successful ranges once.
- Retryable service timeouts (`RequestTimeout` and `RequestTimeoutException`,
  including HTTP 400) retain their transient classification. Permanent errors
  are not retried. Cancellation stops pending retries.
- The lab retains strict 2 IOPS for S3 and configures 8 MiB GETs, giving three
  requests for its `16 MiB + 137` fixture. Baselines use the same request size.
  The lower timing bound includes the first admission's hard-rate slot.
- HEAD/metadata remains outside the payload-read budget, consistent with the
  existing architectural scope. Whole-request admission bounds bursts by the
  configured request size; it does not claim instantaneous TCP receive pacing.

Regression tests first reproduced both defects: low bandwidth yielded 1,600 GETs
instead of three, and two SDK retries yielded three connector GETs but one
reported source operation. Tests now cover both corrected behaviors, bounded
503 retries, permanent 403 failures, service timeouts, and cancellation using the
real AWS SDK with an in-process connector. No external S3 endpoint was contacted.
See [source tests](../../src/storage/backends/s3/source_pipeline_tests.rs),
[SDK connector tests](../../src/storage/backends/s3/client/role_protocol/qos_wire_tests.rs),
and [architecture contract](../architecture/storage-transfer-architecture.md#11-source-only-transfer-qos).

Final verification: 1,671 library tests passed (nine ignored), five public API
integration tests passed, and 20 offline lab/harness contract tests passed.
All-target Clippy with the workflow's denied lints, formatting and diff checks
passed. Real-backend nightly validation has not yet been rerun for this fix.

## Findings

### 1. `source_read_operations` counts admissions, not all GET attempts

**Source observation.** `SourceQosBudget::admit` increments the counter after the
shared scheduling wait succeeds, before returning the granted byte count.
S3 calls this once per scheduled range, then creates a future that invokes
`protocol.get_range`. Thus it normally counts one logical ranged GET invocation
per admission, including an invocation that later fails, rather than successful
responses or HTTP transmission attempts. Cancellation during admission is uncharged;
cancellation after admission can leave a counted operation without a transmitted
GET because the GET future has its own cancellation branch. See
[admission and counter update](../../src/runtime/qos.rs#L180),
[range scheduling and cancellation](../../src/storage/backends/s3/source.rs#L322).

The real client builds one `GetObject` with an inclusive HTTP Range corresponding
to the admitted half-open range, calls `.send().await`, and then collects the body.
It has no `SourceQosBudget` argument and no retry callback into admission. The SDK's
internal retry loop can make additional HTTP attempts inside this one `.send()`;
those attempts do **not** increment this counter or acquire another source IOPS
slot. See [GET implementation](../../src/storage/backends/s3/client/role_protocol.rs#L218)
and the installed, locked SDK runtime's
[attempt loop](/root/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/aws-smithy-runtime-1.13.1/src/client/orchestrator.rs:311).

**Source observation, dependency-specific.** This is not merely a hypothetical
retry feature: the client uses `SdkConfig::builder()` with
`BehaviorVersion::latest()` and no explicit retry override. Locked dependencies
are `aws-sdk-s3 1.129.0`, `aws-smithy-runtime 1.13.1`, and
`aws-smithy-types 1.6.2`. The installed S3 config installs AWS default plugins;
the runtime selects `RetryConfig::standard()` for AWS clients at behavior version
2026-01-12 or later. Its standard configuration has three maximum attempts.
See [client construction](../../src/storage/backends/s3/client.rs#L439),
[lockfile](../../Cargo.lock#L310), and installed dependency source:
`aws-sdk-s3-1.129.0/src/config.rs:1709–1717`,
`aws-smithy-runtime-1.13.1/src/client/defaults.rs:160–197`,
`aws-smithy-types-1.6.2/src/retry.rs:423–433`, under
`/root/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`.
The runtime API's `behavior_version.rs:38–40` resolves `latest()` to 2026-01-12.
The [official Rust retry guide](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/retries.html)
also documents standard retries and three attempts, with transient errors and
throttling among retryable conditions. Actual attempts depend on errors, retry
quota, cancellation, and timeouts; three attempts per range were not observed here.
Because this project builds `SdkConfig` directly rather than using the normal
config loader, generic documentation about environment/profile retry settings
does not by itself establish which overrides this path loads.

**Derived result.** An initial GET followed by two SDK retries can consume one
admission and report one operation despite three wire attempts. The architecture's
rule that an actual retried source read consumes IOPS again is therefore not
implemented for SDK-internal retries. A reread that reaches `next_range` and calls
`admit_read` again is charged; a new transfer attempt gets a new per-attempt meter.
This distinction matters when comparing transfer stats to endpoint request logs.
See [architecture §11](../architecture/storage-transfer-architecture.md#L725).

Payload stats are separate: `record_read_bytes` occurs only after a complete,
correct-length range returns. Failed responses and partial body bytes are not
reported as shaped payload, although admission already consumed scheduling budget.
The production code does not wrap post-response `body.collect()` in a GET retry
loop. For unpinned reads it may issue a diagnostic HEAD instead. See
[delivery accounting](../../src/storage/backends/s3/source.rs#L345),
[body collection](../../src/storage/backends/s3/client/role_protocol.rs#L255), and
[unpinned failure handling](../../src/storage/backends/s3/client/role_protocol/unpinned.rs#L35).
AWS explicitly distinguishes streaming body consumption from API operation
timeouts in its [timeout guide](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/timeouts.html).

### 2. HEAD requests are outside source IOPS accounting and pacing

**Source observation.** None of these paths calls `admit_read`:

| Source request | Trigger | Evidence |
| --- | --- | --- |
| HEAD / versioned HEAD | Source describe | [describe_version](../../src/storage/backends/s3/source.rs#L173) |
| HEAD / versioned HEAD | Each `read()` opens and checks source identity, before range admission | [read opening](../../src/storage/backends/s3/source.rs#L227) |
| Final HEAD | Nonempty read without conditional-read support, when the stream is polled to completion | [confirmation decision](../../src/storage/backends/s3/source.rs#L260), [completion](../../src/storage/backends/s3/source.rs#L313), [HEAD](../../src/storage/backends/s3/source.rs#L376) |
| Diagnostic HEAD | Unpinned GET has a short or broken body | [GET closure](../../src/storage/backends/s3/client/role_protocol.rs#L255), [broken-body branch](../../src/storage/backends/s3/client/role_protocol/unpinned.rs#L55) |

These HEADs use SDK `.send()` too, so any internal retries also bypass source
admission. A simple describe-plus-read sequence has two source HEAD invocations
before GETs, and an unpinned nonempty successful stream adds a final HEAD; this is
not a claim about total requests for an entire transfer, which may perform other
observations. Connection probes and versioning detection are outside this meter
as well. See [HEAD client](../../src/storage/backends/s3/client/role_protocol.rs#L120),
[HeadBucket](../../src/storage/backends/s3/client/role_protocol.rs#L193), and
[connect-time versioning](../../src/storage/backends/s3/client.rs#L465).

This exclusion agrees with the architecture's separate-budget rule for metadata
observation, but means source IOPS is not an all-S3-requests limit. AWS describes
HEAD as retrieving metadata without returning the object body:
[HeadObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

### 3. Low bandwidth increases real range-request count

**Source observation.** Admission grants
`min(requested, max_read_bytes, max(1, ceil(hard_bytes_per_second × 0.010)))`.
With no bandwidth policy, the hard-bandwidth quantum is effectively unlimited.
S3 uses the grant as the actual GET range length; it does not keep a larger GET
open and merely emit smaller chunks. Any source QoS budget also sets its read
depth to one. See [10 ms quantum](../../src/runtime/qos.rs#L10),
[grant calculation](../../src/runtime/qos.rs#L193),
[QoS read depth](../../src/storage/backends/s3/source.rs#L265), and
[GET range construction](../../src/storage/backends/s3/source.rs#L322).

**Derived results**, for `16 MiB + 137 = 16,777,353` bytes, an 8 MiB backend/request
ceiling, full successful ranges, and no rereads:

| Policy read cap | Hard bandwidth | Largest grant (bytes) | Range GET invocations |
| --- | --- | ---: | ---: |
| 64 KiB | None | 65,536 | 257 |
| 8 MiB | None | 8,388,608 | 3 |
| 8 MiB | 1 MiB/s | 10,486 | 1,600 |
| 8 MiB | 8 MiB/s | 83,887 | 200 |
| 8 MiB | 32 MiB/s | 335,545 | 51 |

Counts are `ceil(payload / grant)`, excluding HEADs and SDK retries. A 64 KiB cap
at 8 MiB/s still gives 257 ranges because the cap is smaller than the quantum.
Increasing the cap alone cannot remove amplification when the bandwidth quantum
remains the binding limit. These numbers match cases in the parent's current
[experimental paused-time test](../../src/storage/backends/s3/source_pipeline_tests.rs#L14);
they are independently checked arithmetic, with parent-reported execution below.

More requests do not establish an IOPS-rate violation. With strict 2 IOPS, 1,600
admissions require at least 800 seconds from a fresh scheduler, even though the
bandwidth-only transfer target would be about 16 seconds. A 64 KiB grant at strict
2 IOPS caps ideal payload throughput near 128 KiB/s. These are derived bounds,
not measured durations. Serialized request latency and consumer backpressure can
reduce throughput further. The amplification is caused by this implementation's
grant-to-range mapping, not an AWS requirement. AWS supports ranged GETs and
concurrent range requests; see [S3 performance guidelines](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html).

For strict bandwidth `B`, strict admitted-read IOPS `L`, and full effective GET
size `g`, the ideal steady-state payload throughput is bounded by
`min(B, L × g)` (omit `B` when bandwidth is unset). The final short range,
request latency, and backpressure can lower it. Soft/hard policies require their
separate average and peak envelopes. Admission before a whole GET does not
establish an instantaneous wire-bandwidth ceiling during its body transfer.

### 4. Low IOPS includes a first-operation wait

**Source observation.** Scheduler credit starts at zero, and the hard deadlines
start at group creation. The IOPS soft credit capacity is
`(hard - soft) × peak_duration`; each admission needs one credit or waits for
the deficit at the soft rate. The hard deadline enforces a `1/hard` interval;
after a sufficiently long idle period it uses `now + 1/hard`, rather than
releasing a catch-up burst. The shared FIFO mutex remains held during the wait,
and both dimensions commit at the actual release time. See
[initial state](../../src/runtime/qos.rs#L108),
[combined deadline and commit](../../src/runtime/qos.rs#L213), and
[IOPS timing](../../src/runtime/qos.rs#L296).

**Derived result.** For strict `soft = hard = R`, capacity is zero and every
admission waits at least `1/R` after entering the scheduler. The first operation
is not free: strict 2 IOPS implies at least 0.5 s for it and at least 128.5 s for
257 admissions. For soft/hard 2/4, an immediate fresh-group request initially
waits about 0.5 s; idle time can accumulate up to one credit with a 500 ms peak
duration and shorten an admission toward the 0.25 s hard interval. Group age and
prior work therefore matter. Bandwidth and IOPS deadlines are combined using
`max`, not by adding two independent sleeps. None of this establishes spacing
between SDK retry transmissions, which never return to this scheduler.

### 5. Original lab expectations are stale; no lab fix or pass is claimed

The committed harness expects S3 to use 5 MiB GETs, calculating four operations
for this fixture. It nevertheless supplies `--qos-burst-bytes 65536` to the
same generic policy constructor used by S3. At default 8 MiB/s, and also at the
IOPS profile's 256 MiB/s, this cap predicts 257 admitted ranges. The CLI has no
S3 exception to the cap. The script's IOPS comment also assumes the first
operation is immediately available and checks `(operations - 1) / hard_iops`,
which is weaker than the current fresh-scheduler bound. Sources pinned to HEAD:
[fixture and cap](https://github.com/JayTsu-sh/data-mover-rs/blob/6f083e20d7bd556832b001fc34af5ccc9ebfe209/tests/lab/run-qos-e2e.sh#L25),
[expected count and IOPS profile](https://github.com/JayTsu-sh/data-mover-rs/blob/6f083e20d7bd556832b001fc34af5ccc9ebfe209/tests/lab/run-qos-e2e.sh#L145),
[CLI arguments](https://github.com/JayTsu-sh/data-mover-rs/blob/6f083e20d7bd556832b001fc34af5ccc9ebfe209/tests/lab/run-qos-e2e.sh#L195),
[elapsed-time check](https://github.com/JayTsu-sh/data-mover-rs/blob/6f083e20d7bd556832b001fc34af5ccc9ebfe209/tests/lab/run-qos-e2e.sh#L255),
[README expectations](https://github.com/JayTsu-sh/data-mover-rs/blob/6f083e20d7bd556832b001fc34af5ccc9ebfe209/tests/lab/README.md#L185), and
[CLI policy construction](../../examples/storage_copy.rs#L73).

The harness computes baseline IOPS from an assumed count divided by process
elapsed time, not observed HTTP requests. Its QoS total comes from transfer
stats, not wire telemetry. Consequently those fields cannot prove retry/HEAD
coverage or a wire-attempt ceiling. See the committed script's lines 145–151
and 222–244, and [stats reporting](../../examples/storage_copy.rs#L153).

## Recommendations and design tradeoff

Make the public distinction explicit: admitted payload reads, successful returned
payload bytes, and service-observed total requests are different measurements.
If the intended contract covers every HTTP attempt, place request admission and
attempt telemetry at a seam that SDK retries also traverse, or deliberately own
the retry loop above admission. Decide separately whether HEAD/control requests
share that budget or use the metadata budget described by the architecture.
The predicted SDK retry gap is source-derived; no injected network test proved it.

For amplification, decide which bandwidth envelope is required before changing
range sizing. Larger whole GETs paced by their byte cost reduce requests but permit
larger short-window wire bursts; pacing body consumption may also involve SDK,
HTTP, and socket buffering. Keeping small quantum-sized GETs preserves the current
fine-grained admission behavior at higher request cost. A revised design should
state the allowed burst/window and validate it alongside request count and IOPS.
Arbitrarily raising test IOPS or bandwidth can shorten a run or enlarge its grant,
but does not fix retry accounting or resolve this bandwidth/request-size tradeoff.
Correct the lab's stale expectations only after that contract is clear.

The concrete semantic gap is SDK-attempt coverage; HEAD exclusion is consistent
with a payload-read budget but must be explicit. Small-range amplification is
separately established by the grant formula and test cases. Neither finding alone
proves that the admitted-read IOPS scheduler exceeds its configured rate.
