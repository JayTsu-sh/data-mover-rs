# Separate Local transfer execution, verification, publication and recovery

Policy names and final durability below are superseded by [ADR-0002](0002-auto-and-quick-policy.md): current public policies are Checkpointed (formerly Auto) and AtomicReplace (formerly Quick). The follow-ups below retain their historical rationale.

The recovery-store parts below (engine-owned local records, recovery identities, registration) are superseded by [ADR-0006](0006-destination-resident-recovery.md): recovery state lives beside the final file, and the local recovery store was removed in C21.

Accepted 2026-09-09. Source and destination chunks determine scheduling, not publication guarantees. Local single-source-chunk transfers avoid an inflight producer/channel; multi-source-chunk transfers retain the existing inflight read/write pipeline. Local writes split shared `Bytes` slices at their own 5 MiB ceiling; Local does not require smaller source chunks to be copied or aggregated into a contiguous allocation. A complete source chunk larger than the destination ceiling still uses bounded concurrent positional writes.

Read-back verification is explicitly optional and defaults to enabled. When disabled, skip staged read-back and source content hashing. Successful outcomes expose `read_back` and an optional BLAKE3 digest; absent verification never produces verified-content evidence. Size checks, source identity binding, I/O errors, cancellation, data synchronization and atomic publication remain mandatory.

`RecoveryPolicy::Auto` is the default. Local plans once using the known source size and a destination interval of ten maximum write chunks (50 MiB). Files at or below that interval (50 MiB) create no recovery files. Larger multi-source-chunk transfers begin ephemeral and acquire a claim, persist progress and register recovery at the first checkpoint barrier. Subsequent barriers use completed contiguous bytes, drain earlier writes, synchronize data, then persist the checkpoint. Recovery registration ownership is separate from a valid backend checkpoint, so a failed competing registration cannot delete another transfer's record. `Checkpointed` uses the same deferred threshold behavior; `RestartFromZero` explicitly clears prior recoverable work. Backends without deferred checkpoint support retain their existing policy behavior.

Do not check estimated remaining time or negotiate budgets per chunk. The hot path retains existing backpressure, byte accounting and one checkpoint threshold comparison. In-memory checkpoint eligibility never substitutes for durable backend evidence. A first-checkpoint failure before registration requires restart; a successful durable checkpoint can be exported even if registration subsequently fails. Recovery leases and stage claims prevent competing recovery; failure cleanup preserves unrelated registration state.

A prepared Local stage owns its staging directory capability for its lifetime. Prepare, write, verify and publish reuse that handle, avoiding repeated directory creation and resolution. Handles are not globally cached across attempts. Directory mutation still cannot escape the root capability; filesystem failures remain explicit. Verification buffers are bounded by actual expected file size, with a nonempty buffer even for empty expected content. No guarantee depends on the file fitting one chunk.

Performance follow-up: creation resolves the staging directory and exclusively creates the stage in one blocking task. Single-piece writes open, write and synchronize in one blocking task. Source inflight reads submit blocking I/O directly, without an additional asynchronous task per piece. Overwrite publication does not open the previous destination or unlink the stage name already consumed by rename; ephemeral stages have no checkpoint to unlink. Publication binds its final parent directory once.

Directory durability remains mandatory. Concurrent publication barriers on the same directory inode may share a synchronization round within one backend instance. A caller arriving after synchronization started joins a subsequent round, and each caller receives its own round's result. Each round elects its own caller to run the barrier; completion hands off to the pending round without waiting for later rounds. A failed round does not prevent the pending round from attempting its own barrier. Weak coordination entries retain no directory handles across attempts; there is no batching timer. This optimization does not equate the legacy interface's durability and publication semantics with staged transfer.

At a checkpoint boundary, completed writes establish a contiguous prefix. Its data synchronization and checkpoint persistence overlap the next write window, with at most one checkpoint operation pending. That operation is awaited before another checkpoint starts and before final truncation, error cleanup or publication. A checkpoint must never truncate the file to its older prefix while later writes are in flight. The checkpoint interval is computed once; each piece only compares its issued offset against the next threshold.

Before automatic registration, process failure may leave an unregistered staging orphan; it must not be treated as resumable or deleted merely because it is old. An orphan sweeper with ownership rules is outside this change. Source and destination state formats remain backend-owned. Disabling read-back also disables detection of content corruption detectable only through read-back; callers must select that trade-off explicitly.

Consumer migration: `TransferOutcome::blake3` is now `Option<[u8; 32]>`, with `Some` only after read-back verification. `read_back` records the selected behavior. Code requiring the former eager recovery behavior should explicitly choose `RecoveryPolicy::Checkpointed`; the default is now `Auto`. The expert source/destination interface keeps its verified-evidence contract. When read-back is disabled, recovery reads only the suffix beyond the durable prefix.

Parent-directory staging follow-up (2026-09-10): new Local stages are hidden siblings of the final file, named `.data-mover-<destination-hash>-<process>-<sequence>.stage`. Checkpoints and claims use adjacent suffixes. The `.data-mover-` component prefix is reserved for internal Local files, and Local traversal omits it. The recovery identity retains its opaque root-relative stage path; existing identities in the former root `.data-mover-staging` directory remain readable and recoverable. Recovery does not create missing directories. New target ancestors are synchronized when created. Publication resolves the current final parent and, on Unix, confirms directory inode identity before eliding the second directory sync; moved parents or legacy cross-directory stages retain both barriers. Other platforms conservatively retain both sync calls. Data synchronization, cancellation and atomic publication guarantees are unchanged.

Populated-directory performance follow-up (2026-09-10): Unix publication reads staging inode identity from the existing directory capability. It opens that directory for synchronization only if it differs from the final parent (or uses the legacy layout). The final parent's already-read metadata also supplies the synchronization group's identity, avoiding a second stat. Directory capabilities may be O_PATH on Linux and must not themselves be assumed fsync-capable. Publication still resolves the current final parent and synchronizes both inodes after a parent move.

Finalization follow-up (2026-09-10): Local stage state now retains the creation file handle until its first consumer, plus the validated stage path/name and directory capability. The consumer takes ownership of the cached handle, so completed writes release it in their blocking task instead of deferring the last close to the async transfer task. Cached state is bound to the stage token and final path; recovered stages validate their token again and reopen their file through the existing recovery path. There is no global file-handle cache. The first complete write to a newly, exclusively created empty stage infers its length from the existing contiguous positional-write accounting and skips redundant final `set_len`. The flag is consumed on the first write attempt: repeated writes, failures and recovered stages retain explicit tail normalization. Data synchronization still runs before successful publication; directory synchronization and final-parent re-resolution are unchanged. Multi-source-chunk transfers retain inflight. The no-data-sync diagnostic's large improvement is not assumed to carry over to the durable path: both steps require separate durable performance measurements.

Recovery-policy comparison follow-up (2026-09-10): all three recovery policies retain final data synchronization, atomic publication and directory synchronization for Local. `Checkpointed` skips checkpoints when the entire file fits the effective source chunk (including empty files). Both `Auto` and `Checkpointed` use Local's deferred threshold policy: 10 × 5 MiB maximum destination chunks gives a 50 MiB checkpoint interval, and files at or below one interval (50 MiB) do not create or clean up recovery records. Eligibility requires source size strictly greater than the interval and more than one effective source chunk. Periodic checkpoints run only while bytes remain: a final chunk reaching or crossing a checkpoint boundary proceeds to final synchronization and publication without an extra checkpoint. Eligible copies begin ephemeral, synchronize the first completed checkpoint prefix, and only then acquire recovery authority and register it; final recovery cleanup runs only when registration occurred. Other destinations without deferred-checkpoint support retain their existing behavior. `RestartFromZero` does not create new checkpoints and clears prior registered work if present. The comparison example exposes `--recovery-policy auto|restart-from-zero|checkpointed`; the legacy `--restart-from-zero` alias remains accepted but conflicts with that option. Read-back remains independently optional. Linux early-writeback and preallocation prototypes remain diagnostics and are not enabled in this policy comparison.
